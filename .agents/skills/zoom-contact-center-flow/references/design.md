# 設計と要件確認

## 自然言語から仕様へ

ユーザーが指示した内容を `requirements` に短く整理し、それぞれにID、対応ノード、実行シナリオを付ける。シナリオは出口番号で選ぶ。同名の `Match` が複数あっても曖昧にならない。条件値、案内本文、転送先などの重要な期待値はJSON pointerによるassertで照合する。

シナリオが通っても、自然言語の意味と仕様が一致するとは限らない。Codex自身が以下を照合し、必要に応じてsummaryへ補足する。

| 設計対象 | 確認すること |
| --- | --- |
| 開始条件 | チャネル、エントリポイント、発火方法、既存の開始設定の継承範囲 |
| 案内・入力 | ユーザー指定文言、言語、入力方法、選択肢、入力待ち時間 |
| 分岐 | 全選択肢と条件の順序、無入力、不一致、メディア失敗 |
| 転送 | 実キュー／フロー／担当者、優先度、営業時間、あふれと転送失敗 |
| 再試行 | 回数、状態変数、上限到達後の動作、循環の脱出条件 |
| 終了 | 正常・失敗・転送完了後の違い、実行中に参照する変数の寿命 |

指示のない営業時間判定、録音、SMS送信、CRM連携などを勝手に追加しない。必要性が明らかでも業務動作を決める不足なら確認する。案内の文体調整と、事実・医療判断・緊急時判断などの創作を区別する。

## 標準の共通化

同一処理は合流を許容し、左から右の流れ、分岐順序、出口名と分岐近傍の終端で読みやすくする。次の判断例を固有のウィジェット名に限定せず使う。

- 単純なDisconnectは近傍に複製してよい。多数の案内や条件変更まで連鎖して複製しない。
- キュー前案内は本文・言語・失敗時動作が同じなら共有する。異なる場合は分離する。
- 転送先が同じでも優先度、あふれ処理、後処理が異なるなら別の処理である。
- 共通処理が複数のフローにまたがる場合は確認済みの再利用機能を検討する。共有部分の変更は利用元への影響と正常・失敗の両出口を確認する。

根拠は主要製品のモジュール化指針を踏まえた設計推奨であり、Zoomが全フローの配置を規定した業界統一標準ではない。[出典](sources.md)を参照する。

## 変更ごとの保証

- **配置のみ**: 外側JSONと未知のgraphメタデータ、ノードの順序・名前・ID・設定・出口は保持し、top/leftだけを変更する。
- **分離**: 全ノードから複製元への対応を記録する。各コピーの設定と順序付き出口を元へ戻して比較する。この対応関係は循環を含む処理グラフの同等性を検証するが、外部サービスの状態や時間依存の副作用を実行検証するものではない。
- **新規・処理変更**: 処理が変わるので元との同等性を要求しない。要件と期待値を検証し、その後の配置・分離で指定処理が維持されることを確認する。

コード、変数、他ノード名・IDを参照する式は一般的な文字列置換で移行しない。CLIは曖昧な参照を保留する。形式を調査して経路ごとの参照先を確定できる場合だけ、限定的な移行を実装し、参照と副作用のテストを追加する。

## レイアウトと証跡

ツリーは枝の外形を使って余白を詰める。合流や循環があるグラフは階層化して関連する枝をまとめ、接続線をカードの外へ迂回させる。循環を隠したり、接続線を消して重なりゼロに見せたりしない。

SVGはノード名と出口番号を表示し、長い出口名は省略表示と完全なtitleを持つ。全体図と分岐の拡大図を目視し、重なる線の追いやすさも確認する。必要なら終端の分離、余白、業務単位の分割を調整する。標準モードで合流を残すことは許容される。

`verification.json`のZoom確認欄を更新するのは、実際に確認した時だけ。確認方法、対象バージョン、時刻を併記する。ユーザーの「完璧」はuser_confirmationへ記録できるが、Codex自身の取り込み・実行確認へ振り替えない。
