# Implement

Treat the selected goal as the implementation specification. The current agent owns investigation, implementation, verification, and live behavior checks; do not route work through repository-specific implementer agents, fixed models, or a legacy lifecycle.

## Resolve the plan

- Use the explicit `plans/<slug>/goal.md` path when supplied.
- Otherwise list `plans/*/goal.md`. Continue only when exactly one candidate exists; stop when there are zero or multiple candidates.
- Reject any other filename or depth, reserved legacy slugs, and invalid kebab-case slugs.

## Implement

1. Read repository rules, the complete goal, current Git status, and the affected implementation before editing. Read [goal-quality.md](../plan/references/goal-quality.md) and [ui-prototype-quality.md](../plan/references/ui-prototype-quality.md) in full and apply both.
2. Validate the goal against `plans/template.md` and `goal-quality.md`, including all six headings, concrete completion criteria, every required `UI契約` field, and no unresolved high-impact choice. A compile-time requirement is closed only by an executable typecheck or inspection command, or a concrete assertion over the named API; `維持`, `typecheck`, or `compile-time` alone is insufficient. Treat `production` and `本番` as equivalent semantic descriptions of the same observable completion outcome. Ask the user when a missing decision would materially change behavior.
3. Independently classify the work as UI-affecting when it can change rendered DOM or the accessibility tree, visible or accessible copy, styles or layout, interaction or focus behavior, or responsive behavior. This includes frontend refactors intended to preserve appearance. Do not accept `UI変更: なし` when the goal, affected implementation, or expected diff meets any of these conditions.
4. For UI-affecting work, require `plans/<slug>/prototype/`, a dated `machine parity: 合格 — YYYY-MM-DD — ...`, and a dated explicit `UI承認記録: YYYY-MM-DD — ...` before editing production code, then verify all of the following:
   - Require the canonical `plans/<slug>/prototype/` and complete, non-placeholder values for every `UI契約` field defined by `plans/template.md`.
   - Require the goal to record exactly `approval contract: plans/<slug>/prototype/ui-contract.json — version 1` for the selected slug. A legacy path, a different version, or a generic label is not an approval contract and stops implementation.
   - Require `plans/<slug>/prototype/ui-contract.json` version 1 to pass `prototype-revision.mjs`'s exact schema and semantically match the goal's approval-critical `UI契約` values: `productionBaseline` to `production baseline`, `comparisonConditions` to `comparison conditions`, `baselineStateInventory` to `baseline state inventory`, `themeContract` to `theme contract`, `responsiveContract` to `responsive contract`, `visualInvariants` to `視覚的不変条件`, `intentionalDifferences` to `意図した差分`, `stateAndInteraction` to `stateとinteraction`, `comparisonTargets` to `comparison targets`, and `parityMatrix` to the complete immutable `parity matrix`. Require `comparisonConditions.scroll` to be exactly `{ "x": <non-negative finite number>, "y": <non-negative finite number> }`, with no scalar, shorthand, omitted, or extra value, and later verify those values against the measured `window.scrollX` and `window.scrollY` on both surfaces. Formatting and ordering may otherwise differ, but target IDs, target entry/route/surface, row IDs and `targetId`, matching entry/route/surface, state, exact viewport, theme, breakpoint, referenced invariant/difference IDs, and target × state × breakpoint × theme coverage may not. Compare mutable `parity evidence` to this definition by row ID; do not compare evidence fields as part of the manifest. A missing file, parse or schema error, missing or placeholder value, unresolved evidence row, or contradiction stops implementation before production editing. Do not require revision or evidence records inside the JSON; those remain goal fields and are validated separately.
   - Recompute the prototype revision exactly as defined by `goal-quality.md`. Extract exactly one full `sha256:[0-9a-f]{64}` token from each of the `prototype revision`, `parity evidence`, `machine parity`, and `UI承認記録` fields, ignoring only optional Markdown backticks around the token; reject a field with zero or multiple revision tokens.
   - Require all four extracted revisions to equal the current artifact. Require `parity evidence` and `machine parity` each to identify every immutable manifest row ID exactly once as `<row-id>=pass` before implementation may start; together these goal fields are the `machineParityResults`. Bare row IDs, `all N`, missing statuses, `=pending`, `=fail`, duplicates, missing rows, aggregate-only summaries, and extra rows stop implementation. Require all three evidence/approval records to be dated. `未確認`, `未承認`, a missing or unresolved row, Browser evidence alone, and automated evidence alone all stop implementation. Stale or mismatched revisions stop implementation.
   - Resolve the current checkout with `git rev-parse HEAD`, require its full SHA to equal `productionBaseline.commit`, and inspect every exact path in `productionBaseline.sources` for staged, unstaged, or untracked changes before starting a runtime. Any missing, replaced, dirty, or undeclared material baseline source is drift and stops implementation before production editing; checking only the page file is insufficient.
   - Before starting or reusing any preflight server, capture a baseline of the port 3000 listener and every relevant process, container, Compose service, volume, network, and dependency artifact: record each applicable PID or stable resource ID, LISTEN address, cwd, command, runtime owner, container identity, checkout mount, dependency path or identity, and whether it already existed. Use this complete baseline for ownership decisions and final cleanup.
   - Reuse the real application only when the baseline proves it is the correct runtime from the target checkout and mount. Otherwise start it with the repository-standard method. Record whether it is pre-existing/user-owned or started by the current agent, and verify that its actual URL is exactly `http://localhost:3000`.
   - Build the selected prototype with the command required by `ui-prototype-quality.md`, then run `./dev-prototype.sh <slug>` exactly once for preflight to prove it is serveable. Retain its PID and exact reported URL and reuse that same prototype process for final parity; do not start a second copy. A missing entry point, asset, build, or served parity-matrix state stops implementation. If the process exits while the approved artifact is unchanged, restart it and record the replacement PID and URL. Any prototype-content change requires a new revision, machine parity, and explicit UI approval before implementation may continue.
   - Before editing production code, confirm that the Codex in-app Browser is available and can open both the current real route at `http://localhost:3000` and the exact `http://127.0.0.1:<port>/` prototype URL reported by the launcher. If either surface, the Browser, the required fixture, or authorization is unavailable, stop before production editing; `curl`, screenshots supplied without a live DOM, and source inspection are not substitutes.
   - Approval-time evidence is not current-run evidence. After the runtime and launcher checks above, require the runtime's checkout and commit to match the already-validated `productionBaseline` and recheck that every declared source is still clean. Then, immediately before the first production edit, rerun the entire immutable matrix in the Codex in-app Browser against the current real route and the retained approved prototype process. Do not reuse an earlier run merely because its date or revision matches. Match every row's actual viewport, DPR, measured `window.scrollX` and `window.scrollY` against the contract's exact `scroll: {x, y}`, locale, theme, fixture, authorization, query, route, surface, state, keyboard, and focus conditions; compare screenshots, DOM/accessibility state, relevant computed styles and geometry, console, and network.
   - Produce a separate dated `current-run pre-edit parity` evidence set in the implementation report or working evidence, not in `ui-contract.json` and not by mutating the goal. It must name exactly one current prototype revision, actual real/prototype URLs, the complete baseline source inventory, runtime owner, checkout, commit and route, every actual comparison condition including measured `scroll: {x, y}`, and exactly one `<row-id>=pass|fail` result for every executed manifest row with no bare IDs or missing statuses. There may be no missing, duplicate, aggregate-only, or extra row. Every row must be `=pass` before production editing. If the current runtime identity, any source, checkout, commit, route, fixture, authorization, query, Browser condition, or row result drifts from the approved contract, or any unexplained difference appears, treat approval-time parity and UI approval as invalid for implementation, stop before production editing, and require the goal, manifest, prototype, machine parity, and explicit user approval to be renewed.
5. Treat the approved prototype and `UI契約` as the production target, including every approved entry point, state, and matrix row. Replace mocked data and side effects without silently changing screen structure, copy, component choice, layout, responsive behavior, interactions, DOM, accessibility, or states. Stop for an updated contract, a recomputed revision, renewed machine parity, and renewed explicit approval when a material deviation is necessary.
6. Implement the adopted design while preserving unrelated dirty or untracked changes. The goal does not authorize deployment, destructive data changes, secret access, external writes, or GitHub mutations.
7. If repository evidence contradicts the goal, stop and explain the conflict rather than silently changing scope.

## Verify

Run the smallest relevant checks during development, then the repository-required tests, lint, type checks, builds, and `git diff --check` that apply to the changed scope. Before a build that can share or replace runtime output, stop the exact real-app process or container only when the preflight baseline proves that the current agent started and owns it, then recheck its identity and termination. Never run that build concurrently with a user-owned development server using the target checkout or output directory, and never stop that server: use a demonstrably isolated build that contains the exact current changes, or ask the user to stop it. If neither is possible, report the build as blocked.

### Mandatory live parity for UI-affecting work

1. After the build, restart the real application with the same repository-standard method when the current agent stopped its own preflight runtime. Otherwise reuse the still-running user-owned runtime only when it remains the correct application. Before final parity, re-inspect port 3000 and re-confirm the LISTEN address, PID, cwd, command, runtime owner, container identity, target-checkout mount, and the same comparison conditions recorded for preflight and `ui-contract.json`, and verify that its actual URL is exactly `http://localhost:3000`; do not substitute another port, origin, checkout, mount, owner, runtime configuration, fixture, or authorization state.
2. Reuse the prototype PID and exact `http://127.0.0.1:<port>/` URL retained from preflight. Do not launch another prototype server for final parity; if an unchanged artifact had to be restarted after exit, use and report its recorded replacement PID and URL.
3. Open the real application and prototype in the Codex in-app Browser and repeat the approved parity matrix against the real application at the same actual viewport, DPR, measured `scroll: {x, y}` from `window.scrollX`/`window.scrollY`, locale, theme, fixture, route, and state. Match authorization as well, and complete every row at the representative desktop viewport, 390×844, one CSS pixel before and exactly at every affected breakpoint, and in light and dark themes.
4. For every material state, compare aligned page-content screenshots, DOM and accessibility state, relevant bounding rectangles and computed styles, keyboard behavior, focus order and return, console, and network. Only approved intentional differences recorded in `UI契約` may remain; fix every unexplained UI difference.
5. An unavailable Browser, URL, comparable fixture or authorization state, matrix row, or required evidence makes implementation verification incomplete. Stop and report the blocker rather than claiming completion.
6. After the last relevant change to production code, copy, styles, fixtures, routes, the prototype, or the goal, recompute the prototype revision, require it still to match the approval-time parity evidence, machine parity, UI approval, and current-run pre-edit parity, and rerun the entire matrix in the Codex in-app Browser. Report fresh dated `implementationParityResults` with exactly one prototype revision, actual URLs and comparison conditions including measured `scroll: {x, y}`, runtime ownership, and every immutable manifest row exactly once as `<row-id>=pass|fail` plus its evidence location. Bare IDs, missing statuses, `=pending` after execution, duplicates, aggregate-only summaries, missing rows, and extra rows are invalid; completion requires every row to be `=pass`. Any later relevant change invalidates that evidence and requires another full run.
7. Keep both surfaces available until the final parity run is complete. Compare the current processes, containers, Compose services, volumes, networks, and dependency artifacts with the complete preflight baseline, then clean up only exact agent-owned delta resources after rechecking their PID or stable identity, cwd, command, mount/path, and ownership. Remove a created volume, network, or dependency artifact only when its exact identity is absent from baseline, its creation by the current agent is proven, and removal is part of the repository-standard cleanup for this run. Never run a broad `docker compose down`, `docker compose down -v`, or project-wide stop, and never stop, replace, or remove a user's or pre-existing process, container, service, volume, network, or dependency.

Report implemented behavior, changed paths, commands actually run and their results, live checks, prototype parity, unresolved risks, and preserved unrelated changes. Do not update the goal with progress, invoke shipping automatically, stage, commit, push, or create a pull request.
